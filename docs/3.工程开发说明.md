## 工具与依赖

Node.js 24.16.0、pnpm 11.5.1 固定于 `.nvmrc` 与 `package.json`。直接依赖采用精确版本，传递依赖由 `pnpm-lock.yaml` 固定。Payload 相关包统一版本，Next.js 选择满足其 peerDependencies 的版本；TypeScript 5.9 保持与检查工具兼容。具体安装版本以清单和锁文件为准。

仅允许清单列明的依赖构建脚本，不全局放开第三方脚本。项目不安装或启动 PostgreSQL/Docker，使用用户已有 PG。

技术依据：[Payload 安装及 Next.js 集成](https://payloadcms.com/docs/getting-started/installation)、[Payload PostgreSQL 配置](https://payloadcms.com/docs/database/postgres)。已关闭 `push` 和自动建库，模式变更通过显式迁移执行。

## 配置

| 位置 / 变量 | 说明 |
|---|---|
| `apps/content/.env` / `DATABASE_URL` | 已有 PG 连接串，仅服务端使用；支持 `postgres://` / `postgresql://` |
| `PAYLOAD_SECRET` | 至少 32 字符的随机秘密；示例占位值不被接受 |
| `CONTENT_SERVER_URL` | 内容端完整来源，如 `http://localhost:3000`；不带路径或末尾斜杠 |
| `WEB_ORIGIN` | 用户端允许来源，与实际浏览器地址完全一致 |
| `apps/web/.env` / `VITE_PUBLIC_API_URL` | 公共 API 客户端实际使用的公开地址 |

真实 `.env` 被 Git 忽略。用户端不得配置数据库地址或 Payload secret。可在本机用 `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"` 生成随机 secret，自行写入 `.env`，不把真实凭证贴入开发记录。

## 命令

均在仓库根目录执行。

| 命令 | 行为与前提 |
|---|---|
| `pnpm install --frozen-lockfile` | 按锁文件安装 |
| `pnpm dev:web` | 用户端开发服务，127.0.0.1:5173，无数据库依赖 |
| `pnpm dev:content` | 内容端开发服务，127.0.0.1:3000；需要服务端配置，管理后台还需已有库完成迁移 |
| `pnpm dev` | 同时启动两端；端口占用直接报错 |
| `pnpm build` | 拓扑顺序构建共享包和两应用；内容端校验环境值，不要求数据库在线 |
| `pnpm typecheck` | 两端、共享包和测试配置的严格类型检查 |
| `pnpm lint` | ESLint；共享包禁止依赖 UI/CMS/数据库实现 |
| `pnpm format:check` / `pnpm format` | 检查/格式化代码与配置；已有中文文档保留人工排版 |
| `pnpm test` | Vitest 规则/集成测试；包含规则与本地事务测试，不能代替真实浏览器验收 |
| `pnpm test:e2e` | 先构建用户端并安装 Playwright Chromium/WebKit；运行页面闭环、双标签页、照片、离线和持久化测试 |
| `pnpm db:migrate:create` | 生成待审阅迁移文件，不代表已执行 |
| `pnpm db:check` | 读取 `apps/content/.env`、验证配置并只读检查 PG 连接与 public 表；不输出凭证 |
| `pnpm db:migrate:status` | 使用配置的 PG 查询迁移状态 |
| `pnpm db:migrate` | 显式执行迁移，会修改所配置数据库；仅在确认目标及迁移内容后运行 |
| `pnpm --filter @sidequest/content generate:types` | 生成 Payload 类型 |
| `pnpm --filter @sidequest/content generate:importmap` | 生成后台组件 import map |

Playwright 浏览器安装命令：`pnpm exec playwright install chromium webkit`。Linux 系统库缺失时按其诊断安装系统依赖；CI 使用 `--with-deps`。测试配置使用已构建用户端的 4173 端口。

## 数据库与管理员边界

用户已部署 PG，本轮不创建或维护数据库服务。2026-09-15 用户修正连接配置和密钥后，配置及只读连接检查通过；审阅并执行了 `20260915_081200_initial_payload`，建立 8 张 Payload 基础表，迁移状态为已执行。

当前已实现管理员/编辑角色、任务库、版本、审计、排期与备用配置，详见[主要功能操作说明](./4.主要功能操作说明.md)。`/health` 只表示进程存活，不查询数据库。

首次使用步骤：

1. 配置 `apps/content/.env`，执行 `pnpm db:check` 验证连接。
2. 首次接入尚未初始化的项目库时，审阅迁移后运行 `pnpm db:migrate`；本次已完成，无需重复生成初始迁移。
3. 运行 `pnpm dev:content`，在本机打开 `http://localhost:3000/admin`，设置自己的运营邮箱和独立密码。该密码不同于 PG 密码与 `PAYLOAD_SECRET`，不设共享默认值。
4. 用户创建账号后再验证登录与后续后台操作。首个账号应在服务对外开放前创建；目前服务仅监听本机。
5. 业务种子数据等待 T03 契约和奖励规则确认，再通过后续导入流程加载；当前不填入未经确认的任务或数值。

`PAYLOAD_SECRET` 用于 Payload 的认证签名等加密相关流程，不是数据库密码或用户端本地数据加密密钥。保持随机、私密和稳定，生产轮换需考虑现有登录状态。邮件适配器目前未配置，开发期邮件回退到控制台；生产邮件不在当前已验证能力内。
